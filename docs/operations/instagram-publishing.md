# Guarded one-time Instagram Reels

Implementation status: **local implementation; release gates and explicit post approval still required**. The server has typed request/query/approve/cancel RPCs, a durable receipt, a dedicated executor and a private receipt-backed R2 media adapter. Missing media configuration fails closed when hosting is requested and does not prevent disabled startup. Nothing in this change approves or schedules a real post.

## Authority and immutable binding

`cc.instagram.reel.account` returns only the nonmutating account ID/connection revision with `command-center:read`.

`cc.instagram.reel.request` requires `command-center:operate`; query requires `command-center:read`; approve and cancel require `command-center:approve`. The server supplies the authenticated session and subject, checks the persisted session's scope/expiry/revocation, and never accepts a caller-supplied approval or actor. Approval is a separate explicit call with the exact returned digest. The approval transaction stores the server-generated approval ID, actor, session, approval time and expiry before marking the action approved. No agent Run/dispatcher gains publishing authority.

Version 1 binds the account ID and connection revision (`connectedAtMs`), authorized thread and canonical workspace/path, SHA-256, exact byte count and millisecond duration, untrimmed caption, canonical UTC due time and a 30–300 second late window. Requests must be future-dated within seven days. The approval session must remain valid beyond the entire window. Reconnection, changed bytes/duration/root, changed binding, expired/revoked authority or cancellation prevents further mutations. Changing a post requires fresh review; this implementation has no edit/reactivation path.

The logical identity is a SHA-256 over version, account ID, asset hash and due UTC, independent of tick/run/lease/approval IDs. A different caption, late window or account connection revision cannot bypass an existing post's admission receipt. The exact full caption remains in the binding digest. Receipts are permanent identity tombstones, including canceled and uncertain actions: cancellation never permits automatic replacement or reapproval, and there is no reset path.

## Durable executor

`command_center_instagram_reels` is the one receipt/state table. Conditional `UPDATE ... RETURNING` claims assign an owner, generation and 60-second expiry. Every receipt write is fenced by owner/generation/unexpired lease. Cancellation invalidates the generation. No worker renews a lease while an external request is in flight; expired owners cannot overwrite results or authorize another send.

States are requested, approved, creating, processing, ready, publishing, published, uncertain, canceled and error. The server owns a scoped five-second polling loop, scanning at most 25 due receipts per tick. It does not use generic AutomationRuns/ScheduleRunner/RunDispatcher or depend on PR126/127 runtime fixes. No create or publish POST occurs before the approved due UTC. Preparation therefore consumes some of the bounded late window; exact-second publication is not promised. The late window bounds server sends; a request already sent to Meta cannot be retracted and may commit after transport timeout, leaving an uncertain outcome.

Creation intent is persisted before container creation; publish intent is persisted before media_publish. The exact-string `INSTAGRAM_PUBLISHING_ENABLED=true` guard, persisted approval authority, account revision, file bytes/duration, claim and actual clock window are rechecked immediately before each mutation. The Graph client also guards every POST. Containers must return the expected numeric ID and a known status; only FINISHED can enter a fresh publish intent. Processing is bounded by the late cutoff.

A crash, timeout, interruption, lost response or failed receipt write after an intent makes the outcome uncertain. Neither POST is retried. FINISHED after an uncertain publish does **not** permit retry. Read-only recovery checks container status; PUBLISHED without a saved media ID remains uncertain and requires human reconciliation. Up to three bounded recent-media reads validate response/pagination shape but never infer identity from matching caption/time. Pagination is not followed. A published receipt with a saved media ID retries only permalink GETs, at most three times. Successful publish is retained even when the permalink read fails. Both recovery paths first validate the private account snapshot ID and connection revision against the receipt. Changed, disconnected or expired accounts hold recovery with a durable reason, preserve the uncertain/published result and read budget, and make no Graph calls. Recovery does not inspect the asset or require unexpired approval, a valid mutation window or new mutation authority; matching accounts may continue bounded GET-only recovery.

Receipts include scheduled UTC, approval time, create/publish intent times, and the time a successful publish response was recorded (`publishedAt`). That response time is not a claim of Instagram's exact effect time. Capabilities and credentials never enter receipts.

## Asset and hosting prerequisites

The live adapter resolves the existing thread/project workspace through ProjectionSnapshotQuery and WorkspacePaths; it does not admit caller-supplied arbitrary roots. It canonicalizes containment, streams the exact approved byte count/hash, measures duration using existing `ffprobe` (which must already be available to the deployed server; no binary installation is included), and rejects changes in file identity/size/mtime/ctime across inspection. Inspection is bounded to ten seconds; ffprobe has a five-second timeout and 8 KiB output cap. Graph requests are bounded to fifteen seconds and 256 KiB response bodies.

The hosting adapter accepts one server-owned provider artifact through optional `INSTAGRAM_REEL_MEDIA_RECEIPT_PATH` and `INSTAGRAM_REEL_MEDIA_URL_PATH`. The deployment owner must install the verified JSON receipt and separate signed GET file under canonical absolute paths in an existing private directory owned by the server user (directory mode 0700, files mode 0600 or 0400). Files must be regular, nonsymlink, owner-only, and at most 16 KiB / 8 KiB respectively. Reads use `O_NOFOLLOW`, bounded descriptor reads and stable device/inode/size/mtime/ctime/mode/owner checks against the named file and its directory. Never use a client path or the receipt's `url_artifact` field. Install complete files atomically before pointing configuration at them; do not store either private artifact in the repository or expose it through RPC.

The receipt schema requires verified local/full-GET/range evidence, exact hash, bytes, duration and MP4 content type. It binds the approved asset to bucket `instagram-posts`, the existing account endpoint, and the `instagram/manual/april-riles/20261002/<approved-sha256>.mp4` key. Only connection account `17841463886554034` is admitted by this adapter. The server-owned receipt selects the single retained object; client bindings cannot select a different receipt, URL, bucket or prefix. This integration intentionally does not add a general public-media endpoint, origins, routing, uploads, credentials or grants.

The separate URL must use the exact bucket R2 HTTPS host/path, default-jurisdiction credential scope and the existing signed GET parameter contract. Foreign hosts, redirects, userinfo, ports (including an explicit default port), fragments, malformed or duplicate/missing parameters, invalid calendar dates, mismatched receipt signing time and lifetimes over seven days fail closed. Expiry must exceed both actual time plus one hour and the entire approved due/late window plus one hour. The lifetime check runs again after remote inspection.

Immediately before container creation the host port performs a deadline-bounded streaming GET with SHA-256, exact size and MP4 content-type checks, then a GET range with exact 206/Content-Range/length and matching prefix bytes. It never relies on HEAD, buffers the whole remote asset, follows redirects or emits fetch exceptions containing the private URL. The combined media operation has a 20-second deadline; interruption, oversize, header failure and range failure cancel readers and abort transport. The original authorized local-file inspection remains mandatory. The deployment owner must retain the verified object unchanged through Meta ingestion and the fetching grace period; these reads verify the bytes served during preparation, not a storage write lock or evidence that Meta has fetched the object. The signed URL stays only in memory for the Graph container call and never enters a receipt, RPC response, log or artifact.

The April supoclip export is outside t3-code. Its request must refer to its existing authorized project/thread workspace; this feature does not expand roots or copy the file. No caption or due time is supplied by media configuration.
