# Owner-bound canonical outreach execution

The public server contains a closed `canonical-outreach-v1` profile and its enforcement logic. Deployment-specific account names, paths, Space and repository identifiers, environment identity and Unix identities belong only in the existing owner-only scoped-shell manifest. This change installs no manifest, grants, scheduler configuration or credentials and enables no campaign.

An `executionProfile` has the fixed name, automationId, nodeId, definitionDigest, snapshotDigest, inputPath, credentialReferencePath and a required `binding`. The binding contains exactly project, controller, journal, holdParent, environmentId, spaceId, repositoryId, uid and gid. Unknown fields at either level reject. All strings and numeric identities are bounded. The owner must verify the existing provider credential-reference path is outside the project, journal and hold-parent roles and review the actual private binding against the previously approved deployment scope; generic example values are never production defaults.

The binding's controller must equal its project followed by `/bin/guarded-campaign/guarded_outreach.py`. Project, journal and hold-parent directories must be canonical narrow paths, outside protected operating-system roots, and separate from each other. The credential reference must name one separate read-only file; it may not alias or contain any of those directory roles. Input is one fixed JSON file directly inside the journal. Runtime canonicalization rejects symlink and ancestor escapes, pins descriptors and revalidates identities before launch. Private roles must have available, distinct device/inode identities. This rejects exact-object aliases, including equal-object bind aliases; it does not prove that no descendant bind mount crosses a role boundary. Auditing the actual host mount layout remains an activation prerequisite. The whole nested owner policy participates in the existing durable policy-digest compare-and-set, so edits cannot silently change an admitted execution's authority.

The existing Automation `shell.scoped` route resolves the owner manifest on every dispatch. It verifies the actual server environment and effective UID/GID against the binding, its Space/repository against private configuration, and its job/node against the running durable execution/checkpoint join. The full persisted Automation schema, source definitionDigest and separate exact enriched snapshotDigest must match. The snapshot includes runtime metadata; representation or configuration resync changes require deliberate owner reapproval. Caller claims, a public scheduler payload or an arbitrary profile selector cannot create this authority. Removing the owner entry revokes future dispatches; an already-started process retains its admitted policy until exit.

The only command is `/usr/bin/python3.12 -I -S -B`, followed by the owner-bound canonical controller, `--input` and the fixed input file. Only an owner-approved manifest may append the final `--execute`. No caller script, extra arguments, initializer, root, network toggle or resource flag is accepted. Retryable remains false. Sender, local-weekday cap, serialization, opt-outs, uncertain outcomes and launch hold remain enforced by the unchanged private canonical controller.

Only the bound journal is persistently writable; the existing bounded private temporary filesystem remains. Project, controller, input, credential-reference file, live hold parent, resolver metadata and TLS trust directory are read-only mounts. The canonical controller has a pinned file overlay and the hold parent stays visible at its original path so hold-file recreation is visible. The controller role permits only its bound UID/GID and no world write; trusted host-group mutation remains an explicit integrity dependency. The fixed owner-bound hold-parent role retains the existing read-only metadata exception, without claiming owner-only integrity. Other read-only support paths retain the existing root/executor/ordinary-user ownership checks. No host permissions are changed. The loader never opens credential contents; the existing provider consumes its existing authorized reference.

Network sharing applies only to that fixed command and its subprocesses. It is native network access, not a hostname allowlist and not an agent-session grant. Ordinary jobs retain disabled network, repository isolation and their existing resource policy. The canonical profile alone retains the reviewed address-space ceiling and bounded Node heap. Existing concurrency, CPU, process count, core/file/output/timeout limits, process-group cleanup and filesystem reserve/delta checks remain unchanged. Address space is not a small physical-RSS guarantee, and filesystem monitoring is not an allocation quota. **Activation remains blocked: hard per-run aggregate memory/process/time containment through a supported production launcher is unresolved and requires a separately implemented and reviewed control.**

## Review, activation and rollback

Review this source repair and the exact private binding separately before activation. Do not copy deployment identities into public source, examples, tests, PR discussion or logs. A supported owner deployment must still verify real namespace admission, journal persistence/reopen/lock/rollback, existing provider identity, memory/task headroom and read-only database compatibility. Synthetic tests and a held command are not those proofs. With `--execute`, the canonical launch hold can return before journal or network access. The readiness form omits `--execute` but can reconcile state and requires separate authorization to run.

This source patch creates no data migration or public scheduler field. The previous profile literal and schema are incompatible and fail closed; do not install or translate an actual private entry during this source-only repair. Rollback removes the canonical profile entry before returning to a binary that does not understand it, retaining all journal and rollback data. Preserve remaining campaign readiness gates and the launch hold throughout.

Focused offline tests cover owner identity/Space/job/digests, strict nested policy fields, path escape/role overlap, fixed argv and mounts, changed-policy rejection, service reconstruction, manifest revocation and unchanged ordinary jobs. Injected filesystem tests exercise canonicalization and metadata boundaries before spawn. Existing Runtime and ScheduleRunner regressions are separate from a live end-to-end scheduled provider run. Live Bubblewrap, providers and campaign execution remain untested here.
